# API Documentation

Full interactive OpenAPI docs are auto-generated by FastAPI at `/docs`
(Swagger UI) and `/redoc` once the backend is running — this file is a
narrative companion, not a duplicate of that schema.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/events` | Ingest a network event; runs anomaly detection synchronously; creates an Incident if flagged |
| GET | `/api/v1/incidents` | List incidents (optional `?status=` filter) |
| GET | `/api/v1/incidents/{id}` | Get one incident |
| POST | `/api/v1/incidents/{id}/investigate` | Run the 5-agent LangGraph investigation pipeline |
| GET | `/api/v1/incidents/{id}/investigation` | Get the latest investigation result + agent trail + retrieved evidence |
| GET | `/api/v1/incidents/{id}/recommendation` | Get the recommendation produced by the last investigation |
| POST | `/api/v1/incidents/{id}/approve` | Human approves the recommended action → simulated execution + audit log |
| POST | `/api/v1/incidents/{id}/reject` | Human rejects → incident closed, no action taken |
| POST | `/api/v1/documents/ingest` | Add a document to the live RAG knowledge base |
| GET | `/api/v1/metrics` | Dashboard metrics + detector evaluation report |
| GET | `/api/v1/health` | Liveness/readiness: DB, models, vector store, LLM provider |

## Deviation from the original spec worth calling out
The spec listed a standalone `POST /incidents/{id}/recommendation`. In this
implementation the Response Recommendation Agent runs as the last step of
`POST /investigate` (a recommendation with no completed investigation
behind it would have no evidence to rest on), so that path is `GET` here —
it retrieves the recommendation already produced, rather than triggering a
new one independently of an investigation.

## Auth
Endpoints that change state (`approve`, `reject`, `documents/ingest`)
accept an `approved_by` / actor identity in the request body rather than a
full auth/session system in this build — documented in `SECURITY.md` as
demo-grade, not enterprise SSO.

## Error handling
- Unknown incident ID → `404`.
- Invalid payload (e.g. negative `packet_count`) → `422` (Pydantic validation), never a raw `500`.
- Re-investigating an already-completed incident → `409`.
- Over the rate limit → `429`.
